# Wave plan — 2026-10-18 (from eval-2026-10-18 §3)

Objective unchanged: the buffer-tank system heats efficiently this winter, driven by TempIQ. The eval graded the
**Learning** tier live and the **Safe** tier not met. This plan turns each eval finding into a node that either
**diagnoses** (gathers the fact that decides the fix) or **fixes**, says who owns it, whether it deploys a live
service, what it depends on, and how it is checked. Method unchanged: worktree → tests → Codex until clean → CI with
the named checks PRESENT → a2w deploying merges one at a time through `scripts/deploy-gate.sh`, on a mild day, never
inside a cold band. TempIQ nodes are their own sessions in their own repo.

## 0 · The one fact that reorders everything (F1)

The five dropout windows (Oct 14 15–17Z, Oct 15 18–20Z, Oct 16 10–12Z, Oct 17 05:31–07:41Z, Oct 17 15–17Z) are each
2–3 h long. `deploy/bridge-watchdog.sh` restarts the bridge after 45 min with both W610s unreachable and **reboots the
Pi after 120 min** (6 h cooldown). A Pi whose WiFi has wedged loses the W610s (LAN) and the hub (WAN) at once, so
the ladder fires — and a window of "120 min + boot" is exactly what was measured. Leading hypothesis: **the Pi's WiFi
stalls roughly daily and only the rung-3 reboot recovers it.** The Pi is WiFi-only with eth0 unplugged (#76, 2026-08-07).

Two discriminators, both readable without the house network, because the Pi pushes to the Vercel mirror every 60 s
over a path that does not involve the hub, and that push carries `system_stats.uptime_s`:
- `readings` has a gap exactly over each window → the whole Pi was off the network (not just the hub socket).
- `uptime_s` resets at each reconnect → the reboot ladder ended the window; the dropout was never going to self-heal.
If both are true, the fix is the link, not the software: **wire the Pi on eth0** (strongest), or disable WiFi
power-save / move it to a 5 GHz SSID. Everything else in this plan assumes the link will be fixed; nothing waits on it.

## 3 · Waves

**Wave 0 — now, nothing deploys.** Owner: N11 (runbook), N6o (verify types), N12(i) (inbox), N5 (unpause
OutageWatch), RESEND repo secrets, N13 Tailscale + passphrase. Me: N4 drift-check sections (inert), N8 close-out list for

**Wave 1 — first mild day (lows > 40 °F), deploying, one at a time through the gate.**
1. **#163** (already green) — the first deploy since #162, so it measures the new handover.
2. **N2 + N3 + N10b** in one planner PR, Codex until clean. (Three small, disjoint changes; one handover.)
3. **N1 + N1h** — planner `/health.pi` and the hub dropout counters (two PRs: hub first, it is independent).
Each merge: `deploy-gate.sh merge`, then `railway deployment list` to confirm a deployment exists (the Sept 29 trap).

**Wave 2 — one week of N1 data.** Read the verdict per window; N1p: fix the link (eth0). Done = ≤ 1 dropout/week for
7 days, read from `/health.pi`. Then N4's dropout assertion tightens to 0.

**Wave 3 — before Nov 15.** N6a (and N6b only if the data says so), N9 if a cold night shows stage-2 oddities,
N12(ii) the winter drill, N10c the backup restore + shoulder-season SQL review. **N10a before Dec 1.**

**TempIQ lane — parallel, own sessions.** N7 (statement timeout); push gtm#1590 (delivery_type provenance) so
unverified zones stop being a class.

## 4 · Arms (how each node is checked)

- **Forward** — "what does the first sustained-cold week need?": N2 (no stale-state writes), N1p (the Pi stays up), N11
  (a dead planner reverts), N6o (binding zones have ceilings), N12 (someone is told).
- **Backward** — the eval's measurements are the regression baseline: the five-window table and 14 % Phase B failure
  rate (N1/N1p must drive both to ~0), the 17:55Z I1 violation (N2's scenario reproduces it), the two `set 145°F —
  winter guard` writes (N3's assertion), OutageWatch 502 since March (N5), drift-check red since Oct 11 (N4).
- **Lateral** — the inputs nobody owns: the owner's inbox (N12), TempIQ's readiness check (N7), the board (N8).

## 5 · What this plan deliberately does not do

- No change to the control invariants (I1, I4, caps, 15-min writer limit, single writer).
- No Pi code change: N11 is a config edit; the link fix is physical. The Pi deploys only by `release-*` tag, which is
  the owner's.
- No planner deploy during a cold band or while an identification window is open.
- Nothing against the production database: N10c and the review SQL run on the local restore.
